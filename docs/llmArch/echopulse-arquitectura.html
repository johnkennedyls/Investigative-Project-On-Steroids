Componentes Técnicos Detallados

Módulo 2: MST_MR_Transformer

Retrieval Principal

Arquitectura Transformer Dual (Cross-Attention + Decoder x6)
Input Tokens líricos (máx 151) + Vector técnico (26 features)
Fusión Q: lírica, K/V: técnica → norm_fusion → decoder
Scoring 0.40 × cosine + 0.60 × jaccard
Dataset 5,710 canciones + features técnicos
Output Top 10 candidatos con similarity score
Archivos mst_mr_final.pth (127 MB), embeddings.pt

Módulo 3: IntentTransformer

Re-ranking Semántico

Arquitectura Encoder-Only (4 capas × 8 cabezales)
Input Query EN tokenizado (máx 512)
Clases 38,343 (Spotify IDs desde song_map.pkl)
Fusión Final 0.70 × similarity_M2 + 0.30 × intent_score_M3
Dataset TalkPlayData-2 (~16k diálogos)
Output Top 10 re-ordenado por relevancia
Archivos intent_model.pth (62.8 MB), vocab.json

Decisiones de Diseño Clave

1

Inversión del Flujo (M2→M3)

El Módulo 2 accede a datos técnicos y líricos reales (5,710 canciones), ideal para retrieval amplio. El Módulo 3 está especializado en correlación conversacional (38k clases), ideal para ajuste fino de intención.

2

Fusión Ponderada

Retrieval: 0.40 neural + 0.60 jaccard → Prioriza coincidencia léxica estable.
Re-ranking: 0.70 retrieval + 0.30 intent → Mantiene base técnica pero ajusta por emoción.

3

Robustez en Producción

• torch.nan_to_num() evita errores JSON por similitudes inválidas.
• add_safe_globals([MinMaxScaler]) resuelve bloqueo de PyTorch 2.6+ con sklearn.
• Reintentos exponenciales + wait_for_model mitigan cold starts de HF.

4

Escalabilidad

• Embeddings pre-computados reducen inferencia M2 a <150ms.
• Cache de metadatos en memoria (SONG_METADATA_CACHE) evita I/O repetido.
• Endpoints /api/metrics y /api/health permiten monitoreo sin impactar pipeline.
